# Atleta Personal Helper

Two-product platform: **Streamer** (Twitch/YouTube/Discord tools) and **Racing** (iRacing telemetry & analysis). Each has its own auth system and dedicated landing page. Accounts are optionally linkable.

**Streamer:** Monitors Twitch (live streams, clips, recaps, milestones), YouTube (videos, Shorts, livestreams — hidden from streamers while the `features.youtube` flag is off, as it is now; the YouTube channels already watched keep posting, and livestream detection and the live chat bot also need `YOUTUBE_API_KEY`, which production does not have), and provides welcome messages, subscriber role sync, and weekly digests. Includes chatbots for Twitch and YouTube with customizable thank-you messages, custom commands, 13 built-in fun commands, and chat moderation. OBS overlay with racing-themed animated notification banners, a visual overlay builder with advanced theme editor, and multiple card animations. Channel Point Rewards, giveaways, Twitch polls and predictions, shoutouts, PayPal donations, a multistream relay (switched off until the relay exists), Spotify `!song` integration. Streamers configure everything through `atletanotifications.com`. Requires Discord OAuth login.

**Racing:** Standalone username/password auth (no Discord required). **Atleta Racing** Electron desktop app for iRacing (renamed from "Atleta Bridge" in v3.26.0 — directory `bridge/` and npm package `atleta-bridge` kept for stability) with real-time telemetry overlays and voice-to-chat messaging. Session capture pipeline records per-lap data + 10Hz telemetry traces. Track Database page with Practice/Race tabs. Bridge requires Racing account login on startup.

## Tech Stack

- **Runtime:** Node.js 24 (production image `node:24-slim`, pinned by digest in the `Dockerfile`, with `NODE_ENV=production`; no TypeScript, no build step)
- **Backend:** Express v5, EJS templates (server-rendered)
- **Database:** SQLite via better-sqlite3 (WAL mode, foreign keys)
- **Bot:** discord.js v14 (intents: Guilds, GuildMembers, GuildVoiceStates; nothing the bot posts can ping @everyone, roles or users unless that send opts in)
- **External APIs:** Twitch Helix, Twitch EventSub (WebSocket), StreamElements (socket.io), YouTube Data API v3 + Live Chat API + RSS feeds, Spotify Web API, PayPal, OpenAI Whisper, Anthropic (AI analysis of reported issues)
- **Chatbot:** tmi.js (Twitch IRC) — single shared connection for all channels; YouTube Live Chat API polling
- **i18n:** Custom JSON-based translation system (7 languages); every streamer page and the public tip page are translated (`docs/features/i18n.md`)
- **Deployment:** Docker on Railway with persistent volume at `/app/data`. `railway.json` records the build (the `Dockerfile`, whose `CMD` is the start command), the deploy healthcheck (`/health`, 120 s) and restart-on-failure (10 retries), but Railway is retiring Config as Code files, so the same values are set in the Railway dashboard too. A push to `main` deploys. Service settings, variables, the secrets rollout and rollback cautions: `docs/operations/deploy.md`; backups and restore: `docs/operations/backup-restore.md`.
- **CI:** `.github/workflows/server-ci.yml` runs on pushes and pull requests to `main` (not for `bridge/**`-only changes): `npm ci`, `node --check` on `src/**/*.js`, the unit suite, and two boots in a row on a fresh database with `DISCORD_DISABLED=1` (each must answer `/health` 200, print no `[DB migration]` line, and exit 0 on SIGTERM). No secrets; actions pinned by commit SHA. `.github/workflows/bridge-tests.yml` runs `node --test "bridge/test-*.js"` on pushes and pull requests that touch `bridge/**`.
- **Testing:** `node --test` unit suites (run explicitly; `npm test` is a no-op): `src/**/<name>.test.js` next to the module, `tests/*.test.js` for cross-cutting ones (overlay objects, placement, builder and client; the CSRF client; the translated pages; the shared layout, `headerView.test.js`, and the JSON embeds in views, `scriptEmbeds.test.js`; the Racing views printing stored values as text, `racingViews.test.js`; the multistream relay; the poll bar's model against `pollRules`, `pollBar.test.js`; the locale script, `localeKeys.test.js`), `bridge/test-*.js`. They never touch the network, production or `data/` (stubs, in-memory SQLite, temp dirs). A test that loads `src/db.js` stubs `better-sqlite3`, `fs` and `./config` through `Module._load` (pattern: `src/db.accounts.test.js`), because `db.js` requires `config.js`, which exits without the required env; `src/server.app.test.js` loads the real `server.js` on an in-memory database and talks to it over HTTP (rate-limit keys, the Atleta Racing app's write routes, disabled accounts). The server's Playwright specs are the `tests/*.spec.js` files (never name a unit test `*.spec.js`): `alertObjects.spec.js` (the real overlay at `E2E_BASE_URL`, default `http://localhost:3000`; skipped without `E2E_OVERLAY_TOKEN`) is the only one that honours `E2E_BASE_URL`, and `pitwall.spec.js` (Racing) predates the rule below and hard-codes production, so do not run it as is; the Bridge's overlay specs are in `bridge/tests` with their own config (`bridge/CLAUDE.md`). `tests/playwright.config.js` points `baseURL` at production, so specs must build absolute URLs from `E2E_BASE_URL` and guard with `test.skip` rather than relying on `baseURL`. NOTE: there is currently **no** pre-push git hook — `.git/hooks` contains only samples.
- **Auth:** Discord OAuth (Streamer), bcryptjs username/password (Racing), linkable accounts

For the Bridge desktop app stack (Electron 28, koffi FFI, etc.) see `bridge/CLAUDE.md`.

## Commands

- `npm run dev` — run locally (loads `.env` via `--env-file`)
- `DISCORD_DISABLED=1 TWITCH_CLIENT_ID=x TWITCH_CLIENT_SECRET=x node src/index.js` — run the site without the Discord bot (dev/CI only; no Discord credentials needed)
- `node --test "src/**/*.test.js" "tests/**/*.test.js" "bridge/test-*.js"` — the unit suite (what CI runs)
- `npm start` — production start
- `E2E_OVERLAY_TOKEN=<a streamer's overlay token> npx playwright test -c tests/playwright.config.js alertObjects.spec.js` — the Playwright spec that honours `E2E_BASE_URL` (default `http://localhost:3000`, so start the site first with the `DISCORD_DISABLED=1` command above; the token is the last part of the streamer's `/overlay/<token>` URL). Do not run a bare `npx playwright test`: from the repo root it also selects `tests/pitwall.spec.js`, which is hard-coded to production, and the Bridge's overlay specs in `bridge/tests`

No linting configured.

## Key Architecture

- **Dashboard:** Platform-tabbed main page: Twitch | Discord, then YouTube and Kick while switched on (`features.youtube`, `features.kick`, below), Experimental (`features.vtuber`, and only while `features.overlays` is on too) and Admin (admin-only). A first visit opens Twitch; the tab picked last time (localStorage `dashboard_tab`) opens the next time, and one the page no longer has opens Twitch. A script above the tab bar names that tab on `<html data-dashboard-tab>` and the page's styles show its button and pane, so no other tab is drawn first. Twitch tab: the account row (linked channel, Enable Sub Sync, or Reconnect Twitch), the last 7 days in one strip, then the **working cards** (`views/cards/*.ejs`, in `cards.order`): Chatbot, Discord notifications, OBS overlay, Commands, Shoutouts, Sponsor messages, Donations, Chat protection, Giveaways, Polls & predictions, Channel point rewards, Spotify (the overlay and rewards cards only with `features.overlays`; Multistream last while the relay is configured). A card's switches save as they move and its short texts are edited in a pop-up (`public/js/dashboard-cards.js`); a card that needs the chatbot fades while it is off; a card that is not set up shows its one setup step. The columns fill the window (`repeat(auto-fill, minmax(340px, 1fr))`, packed by the page script). The **Discord notifications** card shows, per claimed server, what it posts about the streamer's own Twitch channel (go-live and clips with their Discord channels, recaps, milestones, weekly highlights, sub roles: on, off, or waiting for the broadcaster authorization), decided as the pollers decide it (`discordNotificationsCard()` in `routes/dashboard.js`), with a link to the server page (its Twitch tab while nothing of the channel is posted there); with no server it offers the bot invite and the servers to claim, and without a linked Twitch account the link to link it. Discord tab shows guild management. YouTube tab has the overlay and chatbot cards; Kick shows "Coming Soon"; Experimental holds the VTuber face tracker (beta). The iRacing page (`/dashboard/iracing`: app download, Bridge logs, Track Database) is no longer a dashboard tab and no view links to it. The working cards save single settings with `POST /dashboard/settings` (JSON `{ key, value, guildId?, id? }` or `{ changes: [...] }`, at most 20, all or nothing): `services/dashboardSettings.js` lists the 68 keys it accepts, how each is read, the single-column writer, what it needs first (`no_email`, `no_role`, `no_channel`) and what follows (`runSettingFollowUps` in `routes/dashboard.js`). - **CSRF:** `src/csrf.js`, mounted after the session middleware and the body parsers, ahead of every route. A POST, PUT, PATCH or DELETE must name this site in its `Origin` (or, without one, its `Referer`): `APP_URL`'s origin or the one the request was sent to; `Origin: null` never counts. Logout is a POST (`/auth/logout`, `/racing/auth/logout`); a GET only redirects.
  - **Adding a form or a `fetch` to a page:** pages get the token as `res.locals.csrfToken`. `header.ejs` includes `views/csrf.ejs`, which loads `public/js/csrf.js` (adds `_csrf` to POST forms as they are sent, `form.submit()` included, and `X-CSRF-Token` to same-origin unsafe `fetch()`/`XMLHttpRequest`), so a page that includes the header needs nothing more. A view that does not include the header must include `csrf.ejs` in `<head>` itself (`overlay-builder.ejs`, `tip.ejs`; the two pages `racing-auth.js` writes out use `csrfScript(res)`); `src/csrf.test.js` checks every view and fails when one is missing.
  - **Adding a route that a program, not a browser page, calls with an unsafe method** (the Atleta Racing app, the multistream relay, a webhook): add it to `CSRF_EXEMPT` in `src/csrf.js` with its reason, or it gets 403 (`[CSRF] Refused ...` in the log). Twitch's refusals become codes with texts (`pollRules.ERRORS`): `twitch_failed` only for no answer in time, no network, a 429 or a 5xx; any other refusal the card does not recognise is `refused` ("check the question, the choices and your channel's settings"; Twitch's message is logged, never shown); `not_affiliate` also stores `cp_affiliate_status = 'not_affiliate'` when the stored flag says otherwise, the flag the rewards card reads (Check again, `POST /dashboard/api/polls/affiliate-check`, clears it; a start Twitch accepts replaces it with `'ok'`, also in that start's answer). A call to Twitch (`twitchPolls.js`) has one deadline of 15 s for the request, a token refresh and the request again together (each request still has its own 10 s), so a start answers before the card gives up at 20 s; a stored token past its expiry is refreshed before the request, and a call refreshes at most once. The on-stream bar is an OBS source of its own, `/overlay/poll/<token>?lang=<lang>` (`public/overlay/poll.js`; `pollModel.js` is shared with the card), fed on the bus channel `poll:<streamerId>` (never `overlay:<id>`): the prediction when both run, a result for 10 s, nothing otherwise; an open bar asks again every 5 s while a poll or prediction runs (so a streamer without an EventSub connection, overlay and chatbot both off, still sees the counts move; while EventSub talks no read is made), and at most once a minute while a prediction stays locked (the `BAR_*` constants in `routes/overlay.js`); exactly one viewer on an outcome reads "1 viewer", and a winning outcome nobody picked has no line under it; its link is on this card and the OBS overlay card while `features.overlays` is on.
- **Shoutouts** (`services/shoutouts.js`, `views/cards/shoutouts.ejs`): `!so @name` from the broadcaster or a moderator (by their badges; `shoutout_command_enabled`, off by default; a viewer's `!so` goes on to the other commands; while the switch is on, a moderator's or the broadcaster's `!so` without a valid name gets no answer, a custom `so` command included) and a shoutout for the raider after a raid of at least `shoutout_raid_min_viewers` (1, 2, 5, 10, 25, 50 or 100; `shoutout_raid_enabled`, off by default; while the chatbot is off the raider is not looked up and their minute stays free). The line is the streamer's `shoutout_template` with `{name}`, `{game}`, `{title}` and `{link}` from Twitch (Get Users, Get Channel Information, with the app token, under one 10 s deadline for both; each name's answer kept 10 minutes); the same person at most once a minute per channel; an unknown name or a failed lookup posts nothing (logged). `!so` posts at command priority, the raid shoutout at normal priority after the raid thank-you; Test in chat (`POST /dashboard/shoutouts/test`) shouts out the streamer's own channel.
- **Errors and deadlines:** `src/errorHandler.js` is the last middleware, so a thrown error is logged with the route pattern (never the real token in the URL) and the visitor gets a generic page, or `{ error: 'Internal error' }` for API/JSON requests, never a stack. Redirects carry error *codes* (`?error=not_found`), never text; the page maps a code it knows to a `t()` key (`errorMessage()` in `donationSettings.js`). Outbound calls have deadlines (`AbortSignal.timeout()`: 10 s for Helix and OAuth), and a dashboard page never waits on Twitch or YouTube for more than 3 s (`pageLookups.js`; missing channel pictures are filled in after the page is sent). The test buttons share one cooldown per streamer, 5 s (`testCooldown.js`).
- **No ORM:** All SQL is raw in `db.js`.
- **i18n:** `t(lang, key, params)` helper via `res.locals.t` (`esc()` and `rich()` are on `res.locals` next to it, set in `src/server.js`); the language is the `lang` cookie (the language switcher), else English; the browser's `Accept-Language` is not used. Every streamer page and the public tip page are translated into the 7 languages: no English typed into a view, every key in `en.json` exists in all 7 locale files with the same `{{placeholders}}` and no empty text, and every key the source names is in `en.json` (`tests/i18n.test.js` enforces it), a sentence with a link, bold word or code is printed through the escaping `rich()` (with `esc()` for plain values; never `<%- t() %>`), a page's script gets its texts as one JSON object, and error codes — not texts — travel in URLs. How to add a string or a page, the tests that guard it and what is deliberately not translated: `docs/features/i18n.md`.

## Conventions

- Plain CommonJS (`require`/`module.exports`), no ESM.
- No framework abstractions — routes, DB queries, and pollers are straightforward procedural code.
- All database operations go through `src/db.js`.
- Config access via `require('./config')`.
- `-1` means unlimited in tier limits.
- CSS design system uses CSS custom properties (defined in `header.ejs`).
- Typography: Outfit (display) + DM Sans (body) via Google Fonts.
- All user-facing text uses `t('key')` — views, the texts a page's script needs, and the answers of routes. No English typed into a view; a new key goes into all 7 locale files (`tests/i18n.test.js` fails without them; `docs/features/i18n.md`).
- Twitch notifications sent as embeds, clips and YouTube videos sent as plain text (for Discord auto-preview).
- Custom alert sounds are stored per streamer in `data/sounds/<streamerId>/<type>.mp3` (persistent volume) and served by `GET /overlay/sounds/:token/:type`; there is no shared sound folder (`public/overlay/sounds/` is an empty placeholder, not a place for sounds). The looks' own recordings are not uploads: they live in `public/overlay/objects/sounds/<family>/` with their content hash in their names, and `node scripts/look-sounds.js` rewrites their manifest after one is added or replaced (docs/features/look-sounds.md).
- Sponsor images stored in `data/sponsors/<streamerId>/`, served via the `/sponsors/` static route.
- Channel point reward media stored in `data/redemptions/{streamerId}/`, served via `/redemptions/`. Filenames are `{rewardId}_{timestamp}.{ext}` so the 24h cache headers stay safe across replacements.
- **EJS templates DO NOT have access to `require()`.** Express's EJS integration runs templates in a sandboxed scope. If a view needs a value derived from a service module, the route handler must compute it server-side and pass it as a template local. Inline `<% require('...') %>` will throw "require is not defined" and crash the page in production. Reference: `routes/dashboard.js` `GET /redemptions` precomputes `hasScope` via `hasRedemptionScope(req.streamer)` and passes it to `redemptions-config.ejs`.
- **Views:** a view that includes `header.ejs` ends with `<%- include('footer') %>` (`tests/headerView.test.js`); a value a page prints into its own script as JSON ends in `.replace(/</g, '\\u003c')` so it cannot end the script (`tests/scriptEmbeds.test.js` checks every `<%- JSON.stringify(...) %>`). The icon library (lucide) loads from one exact version with its `integrity` sha384 in `header.ejs` and `racing-pitwall.ejs`; to move it, download the file, take `openssl dgst -sha384 -binary lucide.min.js | openssl base64 -A` and change both tags (a hash that does not match makes the browser refuse the script, and every icon disappears).
- **Client/server query-param parity for raw-body uploads.** Sponsor/redemption uploads send file bytes in the body and metadata in `?...` query params. The exact param names must match the server's `req.query.X` reads — a mismatch is silent (e.g., empty title gets re-rejected by length validation with a confusing error). When changing one side, verify the other.
- Overlay designs stored in `overlay_designs` table (including `card_custom_x`/`card_custom_y` for drag positions, advanced theme: `bg_opacity`, `gradient_direction`, `border_thickness`, `border_opacity`, `glow_intensity`, `shadow_*`), applied at runtime in `overlay.js` via `applyCustomDesign()`.
- `applyCustomDesign()` must NOT overwrite dynamic detail text for donations/subs/bits/raids — only for follows.
- Tab persistence uses `localStorage` across all tabbed pages.
- Open Graph meta tags in `header.ejs` for social sharing previews.
- Domain: `atletanotifications.com` (Cloudflare DNS → Railway).
- **Pitwall static route Cache-Control split** (`/pitwall/overlays` in `src/server.js`): `.html`/`.js` get `no-cache, no-store, must-revalidate` so deploys ship fresh overlay code immediately; all other assets (SVG flags, PNG helmets, CSS, images) get `public, max-age=3600`. Without the split, the standings/relative overlays' rebuild loop forced a fresh network round-trip per `<img class="flag-img">` and produced a visible flicker on every flag. Keep this split if you ever change static-file headers.
- Public tip pages at `/tip/:username` are NOT behind auth middleware.
- **Public API endpoints (placed BEFORE the `/api` auth middleware in `server.js`, and after the one `apiLimiter`):**
  - Track maps: `GET /api/track-maps`, `GET /api/track-map/:name`, `POST /api/track-map`
  - Sessions: `POST /api/session`, `POST /api/session/:id/lap`, `PATCH /api/session/:id/finish`, `GET /api/sessions/:trackName`, `GET /api/session/:id`, `GET /api/session/share/:token`
- Racing auth endpoints (`/racing/auth/*`) are public. Other `/racing/*` routes (except `/` and `/signup`) require `req.racingUser`.
- Team routes mounted at `/racing/teams` (not `/racing/team`). Old `/racing/team` URL redirects. Detail routes use `/racing/teams/:teamId/...`. Max 5 teams per user enforced in both routes and DB transactions.
- `racing_sessions` table is separate from web auth `sessions` table. Query functions: `getRacingSessionById` / `deleteRacingSession` to avoid collision with web auth session functions.
- `racing_users` table uses `COLLATE NOCASE` for username (case-insensitive login).
- `process.on('unhandledRejection')` and `uncaughtException` handlers in `src/index.js` log and continue (long-running server must not crash on a single bad promise).
- Token refresh paths in `src/services/twitch.js` and `src/services/spotify.js` use in-flight promise locks (per-streamer for spotify, single global for twitch app auth) to prevent concurrent callers from racing parallel refresh requests. The broadcaster token has a per-streamer lock too, `refreshBroadcasterTokenShared` in `twitch.js`, shared by the follow checks and the polls client (both refresh a token past its stored expiry before their request; the polls client refreshes at most once per call): a refresh token Twitch no longer accepts clears the stored scopes, and any other refresh failure stays retryable.
- In-memory Maps and caches get a sweeper that drops stale entries and is `.unref()`'d so it does not hold the process. Pattern: `chatModeration.js` (`permits`, `lastMessages`, `followCache`, `offenseCounts` and the compiled banned-word matchers, swept every 60 s); also `testCooldown.js`, `messageDedupe.js`.
- Security patterns: escape user content (EJS `<%= %>`, `textContent`, the escaping `rich()`); validate and clamp on the server — HTML `min`/`max` are a convenience; compare secrets with `crypto.timingSafeEqual`; give every outbound `fetch` an `AbortSignal.timeout()`; a new token column goes through `sealToken()`/`openToken()`.
- **Rate limits count per visitor address.** Behind Cloudflare that is the `CF-Connecting-IP` header, trusted only when the request reached Railway from one of Cloudflare's published address ranges (`CLOUDFLARE_RANGES` in `src/clientIp.js`, dated — update them if Cloudflare publishes new ranges: until then requests through a new range count as one shared Cloudflare address); otherwise `req.ip` (`trust proxy 1`). The Racing sign-in log records the same address.
- **`.dockerignore` excludes `bridge/*` BUT re-includes `bridge/overlays` + `bridge/overlays/**` at the bottom of the file** so the pitwall iframes can be served from `/pitwall/overlays/*` on Railway. Without the re-include, `bridge/*` would drop the pitwall's overlay files (HTML, SVG flags, PNG helmets). Keeps the Railway image lean (577MB `bridge/` is mostly Electron node_modules) while still shipping the 3.4MB overlay HTML/SVG/CSS/JS the pitwall needs. Other `.dockerignore` excludes: `node_modules`, `.git`, `.gitignore`, `.github`, `data`, `docs`, `tests`, `test-results`, `*.md` and `*.png` (these match only files at the repository root, such as the `helmet-*.png` previews, not files inside folders, so the Setup Guide's `public/screenshots/step-*.png`, about 11 MB, ship in the image: `/tutorial` needs them), `bun.lock`, `.claude`, `.playwright-mcp`, `.superpowers`, `.env*`, `public/vtuber` (a leftover: the repository has no such folder any more).
- `.worktrees/` is gitignored — used for isolated branches during subagent-driven development.

## Overlay Consistency Rule

**The overlay builder (`overlay-builder.ejs`) is the source of truth for how alerts look.** The actual OBS overlay (`overlay.js` + `overlay.css`), the overlay config preview (`overlay-config.ejs` iframe), and the builder preview must all render cards identically:

- **Placement:** where an alert sits (the nine grid cells, a dragged `card_custom_x/y`, and `card_width`) is read from the saved design by `public/overlay/placement.js`, which both the OBS overlay (`applyPlacement()`) and the builder's stage (`placeStage()` in `public/js/builder-cards.js`) use. The five object types honour position and width; their colours and animations are not styled yet.
- **Object registry:** The five Twitch event types (`follow`, `subscription`, `bits`, `donation`, `raid`) render from `public/overlay/objects/`. Any change to an object's markup, keyframes or timing is made there and nowhere else — both render paths (the OBS overlay `overlay.js` and the builder preview `overlay-builder.ejs`) consume the same module. Styles (`STYLES` in `objects/index.js`, `window.ATLETA_OBJECT_STYLES` in the browser) are objects filed under a style id with the `eventType` they draw; both render paths pick an alert's object with the same rule (`objectFor()` in `overlay.js`, `previewObjectFor()` in the builder; `tests/overlayBuilder.test.js` fails when the two picks differ: "the preview and the OBS overlay pick the same object for every alert and style"). `STYLES` is a non-enumerable property of the CommonJS export, so `Object.keys(OBJECTS)` is still the five. `overlay-config.ejs` previews via an iframe of the real overlay and needs no parallel change. Every object-internal CSS class MUST be namespaced under its `.o-*` prefix; a bare `.rail` collides with the builder page's sticky control bar, as shown in the prototype at `docs/superpowers/specs/assets/2026-10-09-alert-objects-prototype.html`. Remaining event types still share the legacy `top-accent` + `card-body` + `car-track` structure, whose markup `buildBannerContent()` in `overlay.js` builds.
- **Looks:** the alert looks (`objects/kit.js`, `objects/styles/`) are drawn by both pages from the same files. The builder's `previewObjectFor` and the overlay's `objectFor` pick with the same rule (`tests/overlayBuilder.test.js` runs both). A look's data comes from `kit.lookData`, its colour and speed from `kit.slotVars`, its effect and sound from `kit.effectFor`/`kit.soundFor` (an alert with no look stored is handed its default look's own settings by both: `kit.ownSettings` through `designOf()` in the overlay, the same reset through `untouched()` in the builder; `tests/builderStylesCore.test.js` checks they agree), and its five new screen effects from `fx.js` (`spawnEffects` and `renderScreenEffect` both call `ATLETA_FX.spawn`).
- **Screen effects:** Direction-based effects (up/down/left/right) must work in both the builder preview (`renderScreenEffect()` in overlay-builder.ejs) and the OBS overlay (`spawnEffects()` in overlay.js). CSS classes for effects must NOT hardcode positional properties (`top`, `left`, etc.) — positions are set dynamically by JS based on direction.
- **Design application:** `applyCustomDesign()` in overlay.js and `updatePreview()` in overlay-builder.ejs (the legacy cards' stage: sponsor images and the YouTube alerts) must apply the same visual properties (colors, fonts, sizes, border-radius, animations, side icons). The default side icons are the builder's table: `DEFAULT_SIDE_ICONS` in overlay.js lists the alerts the builder gives one (`tests/overlayClient.test.js` fails when they differ). A legacy card fades out only once its entrance is taken off (`.entering` and the inline `animation`), because the entrance's last frame holds the opacity.
- **When adding/changing any visual property:** Update all three places — the builder preview (`updatePreview()` in `overlay-builder.ejs`), the OBS overlay (`buildBannerContent()` and `applyCustomDesign()` in `overlay.js` for the legacy cards; the five Twitch events come from `public/overlay/objects/`, which both pages already share), and the shared defaults and save schema in `src/services/overlayDesign.js` (`EVENT_DEFAULTS`, which the route injects into the builder page, and `FIELD_SPECS`; `overlayDesign.test.js` fails when the builder's controls drift from them).
