# Atleta Personal Helper

Two-product platform: **Streamer** (Twitch/YouTube/Discord tools) and **Racing** (iRacing telemetry & analysis). Each has its own auth system and dedicated landing page. Accounts are optionally linkable.

**Streamer:** Monitors Twitch (live streams, clips, recaps, milestones), YouTube (videos, Shorts, livestreams — hidden from streamers while the `features.youtube` flag is off, as it is now; the YouTube channels already watched keep posting, and livestream detection and the live chat bot also need `YOUTUBE_API_KEY`, which production does not have), and provides welcome messages, subscriber role sync, and weekly digests. Includes chatbots for Twitch and YouTube with customizable thank-you messages, custom commands, 13 built-in fun commands, and chat moderation. OBS overlay with racing-themed animated notification banners, a visual overlay builder with advanced theme editor, and multiple card animations. Channel Point Rewards, giveaways, PayPal donations, a multistream relay (switched off until the relay exists), Spotify `!song` integration. Streamers configure everything through `atletanotifications.com`. Requires Discord OAuth login.

**Racing:** Standalone username/password auth (no Discord required). **Atleta Racing** Electron desktop app for iRacing (renamed from "Atleta Bridge" in v3.26.0 — directory `bridge/` and npm package `atleta-bridge` kept for stability) with real-time telemetry overlays and voice-to-chat messaging. Session capture pipeline records per-lap data + 10Hz telemetry traces. Track Database page with Practice/Race tabs. Bridge requires Racing account login on startup.

## Tech Stack

- **Runtime:** Node.js 24 (production image `node:24-slim`, pinned by digest in the `Dockerfile`, with `NODE_ENV=production`; no TypeScript, no build step)
- **Backend:** Express v5, EJS templates (server-rendered)
- **Database:** SQLite via better-sqlite3 (WAL mode, foreign keys)
- **Bot:** discord.js v14 (intents: Guilds, GuildMembers, GuildVoiceStates; nothing the bot posts can ping @everyone, roles or users unless that send opts in)
- **External APIs:** Twitch Helix, Twitch EventSub (WebSocket), StreamElements (socket.io), YouTube Data API v3 + Live Chat API + RSS feeds, Spotify Web API, PayPal, OpenAI Whisper, Anthropic (AI analysis of reported issues)
- **Chatbot:** tmi.js (Twitch IRC) — single shared connection for all channels; YouTube Live Chat API polling
- **i18n:** Custom JSON-based translation system (7 languages); every streamer page and the public tip page are translated (`docs/features/i18n.md`)
- **Deployment:** Docker on Railway with persistent volume at `/app/data`. `railway.json` records the build (the `Dockerfile`, whose `CMD` is the start command), the deploy healthcheck (`/health`, 120 s) and restart-on-failure (10 retries), but Railway is retiring Config as Code files, so the same values are set in the Railway dashboard too. A push to `main` deploys. Service settings, variables, the secrets rollout and rollback cautions: `docs/operations/deploy.md`; backups and restore: `docs/operations/backup-restore.md`.
- **CI:** `.github/workflows/server-ci.yml` runs on pushes and pull requests to `main` (not for `bridge/**`-only changes): `npm ci`, `node --check` on `src/**/*.js`, the unit suite, and two boots in a row on a fresh database with `DISCORD_DISABLED=1` (each must answer `/health` 200, print no `[DB migration]` line, and exit 0 on SIGTERM). No secrets; actions pinned by commit SHA. `.github/workflows/bridge-tests.yml` runs `node --test "bridge/test-*.js"` on pushes and pull requests that touch `bridge/**`.
- **Testing:** `node --test` unit suites (run explicitly; `npm test` is a no-op): `src/**/<name>.test.js` next to the module, `tests/*.test.js` for cross-cutting ones (overlay objects, placement, builder and client; the CSRF client; the translated pages; the shared layout, `headerView.test.js`, and the JSON embeds in views, `scriptEmbeds.test.js`; the Racing views printing stored values as text, `racingViews.test.js`; the multistream relay), `bridge/test-*.js`. They never touch the network, production or `data/` (stubs, in-memory SQLite, temp dirs). A test that loads `src/db.js` stubs `better-sqlite3`, `fs` and `./config` through `Module._load` (pattern: `src/db.accounts.test.js`), because `db.js` requires `config.js`, which exits without the required env; `src/server.app.test.js` loads the real `server.js` on an in-memory database and talks to it over HTTP (rate-limit keys, the Atleta Racing app's write routes, disabled accounts). The server's Playwright specs are the `tests/*.spec.js` files (never name a unit test `*.spec.js`): `alertObjects.spec.js` (the real overlay at `E2E_BASE_URL`, default `http://localhost:3000`; skipped without `E2E_OVERLAY_TOKEN`) is the only one that honours `E2E_BASE_URL`, and `pitwall.spec.js` (Racing) predates the rule below and hard-codes production, so do not run it as is; the Bridge's overlay specs are in `bridge/tests` with their own config (`bridge/CLAUDE.md`). `tests/playwright.config.js` points `baseURL` at production, so specs must build absolute URLs from `E2E_BASE_URL` and guard with `test.skip` rather than relying on `baseURL`. NOTE: there is currently **no** pre-push git hook — `.git/hooks` contains only samples.
- **Auth:** Discord OAuth (Streamer), bcryptjs username/password (Racing), linkable accounts

For the Bridge desktop app stack (Electron 28, koffi FFI, etc.) see `bridge/CLAUDE.md`.

## Commands

- `npm run dev` — run locally (loads `.env` via `--env-file`)
- `DISCORD_DISABLED=1 TWITCH_CLIENT_ID=x TWITCH_CLIENT_SECRET=x node src/index.js` — run the site without the Discord bot (dev/CI only; no Discord credentials needed)
- `node --test "src/**/*.test.js" "tests/**/*.test.js" "bridge/test-*.js"` — the unit suite (what CI runs)
- `npm start` — production start
- `E2E_OVERLAY_TOKEN=<a streamer's overlay token> npx playwright test -c tests/playwright.config.js alertObjects.spec.js` — the Playwright spec that honours `E2E_BASE_URL` (default `http://localhost:3000`, so start the site first with the `DISCORD_DISABLED=1` command above; the token is the last part of the streamer's `/overlay/<token>` URL). Do not run a bare `npx playwright test`: from the repo root it also selects `tests/pitwall.spec.js`, which is hard-coded to production, and the Bridge's overlay specs in `bridge/tests`

No linting configured.

## Key Architecture

- **Dashboard:** Platform-tabbed main page: Twitch | Discord, then YouTube and Kick while switched on (`features.youtube`, `features.kick`, below), Experimental (`features.vtuber`, and only while `features.overlays` is on too) and Admin (admin-only). A first visit opens Twitch; the tab picked last time (localStorage `dashboard_tab`) opens the next time, and one the page no longer has opens Twitch. A script above the tab bar names that tab on `<html data-dashboard-tab>` and the page's styles show its button and pane, so no other tab is drawn first. Twitch tab: the account row (linked channel, Enable Sub Sync, or Reconnect Twitch), the last 7 days in one strip, then the **working cards** (`views/cards/*.ejs`, in `cards.order`): Chatbot, Discord notifications, OBS overlay, Commands, Sponsor messages, Donations, Chat protection, Giveaways, Channel point rewards, Spotify (the overlay and rewards cards only with `features.overlays`; Multistream last while the relay is configured). A card's switches save as they move and its short texts are edited in a pop-up (`public/js/dashboard-cards.js`); a card that needs the chatbot fades while it is off; a card that is not set up shows its one setup step. The columns fill the window (`repeat(auto-fill, minmax(340px, 1fr))`, packed by the page script). The **Discord notifications** card shows, per claimed server, what it posts about the streamer's own Twitch channel (go-live and clips with their Discord channels, recaps, milestones, weekly highlights, sub roles: on, off, or waiting for the broadcaster authorization), decided as the pollers decide it (`discordNotificationsCard()` in `routes/dashboard.js`), with a link to the server page (its Twitch tab while nothing of the channel is posted there); with no server it offers the bot invite and the servers to claim, and without a linked Twitch account the link to link it. Discord tab shows guild management. YouTube tab has the overlay and chatbot cards; Kick shows "Coming Soon"; Experimental holds the VTuber face tracker (beta). The iRacing page (`/dashboard/iracing`: app download, Bridge logs, Track Database) is no longer a dashboard tab and no view links to it. The working cards save single settings with `POST /dashboard/settings` (JSON `{ key, value, guildId?, id? }` or `{ changes: [...] }`, at most 20, all or nothing): `services/dashboardSettings.js` lists the 57 keys it accepts, how each is read, the single-column writer, what it needs first (`no_email`, `no_role`, `no_channel`) and what follows (`runSettingFollowUps` in `routes/dashboard.js`). The Twitch tab's working cards get their state from `services/dashboardCards.js` (`buildCards()`, pure and tested), fed by `gatherCards()` in `routes/dashboard.js`; `GET /dashboard/api/cards` answers their status lines and counts after a change. The page script `public/js/dashboard-cards.js` (helpers in `dashboard-cards-core.js`, dual-exported and tested in `tests/dashboardCardsCore.test.js`) saves each switch through its own queue (the newest value wins; a refused one flips back with the reason and, for `no_channel`/`no_role`/`no_email`, a link to the page that sets it), refreshes the status lines from `GET /dashboard/api/cards`, packs the columns, and says "Your session ended" when a request is redirected (it sends `redirect: 'manual'`: the redirect to sign in leads off the site, to Discord, where `fetch` can only fail) or answered with a 401 or 403 page instead of JSON; any other answer that is not JSON says it did not work, and a request not answered in 20 s counts as no network. Its texts come from `window.ATLETA_CARD_TEXTS` in `dashboard.ejs`; `tests/dashboardCardsCore.test.js` compiles both files, and `src/routes/dashboard.test.js` fails when the script reads a text that table does not hold. The dashboard uses a wide container (`wideLayout`, at most 1760 px); every other page keeps 920 px.
- **OBS Overlay:** EventSub receives Twitch events → `overlayBus` EventEmitter → SSE push to OBS browser source. Centered card design with per-event themes and full-screen effects. The five Twitch event types (`follow`, `subscription`, `bits`, `donation`, `raid`) render from the shared object registry in `public/overlay/objects/` (see Overlay Consistency Rule below). An alert whose saved design carries a `style` (`overlay_designs.style`) is drawn in that look instead (`objectFor()` in `overlay.js`; the looks are under **Alert styles** below). The four connections a logged-in streamer starts from the dashboard (Twitch, broadcaster, YouTube, Spotify) each use a random `state` in a short-lived per-flow cookie (`oauthState.js`); the callback never takes the streamer from the URL. The broadcaster callback asks Twitch (`/oauth2/validate`) whose token it is, refuses one that belongs to another Twitch account than the linked one (a banner names the right one), and stores the scopes Twitch actually granted. Linking a different Twitch account clears that streamer's broadcaster authorization (tokens, expiry, scopes: `db.linkTwitch`), stops EventSub and moves the chat bot to the new channel (`accountLifecycle.twitchAccountChanged`); the streamer authorizes again with "Enable Sub Sync". A streamer whose account another streamer links gets the same treatment; linking the same account again only updates the names. Viewers link Twitch to Discord with the bot's `/link`: the URL is signed (`LINK_SIGNING_SECRET`, valid 15 minutes, `linkSignature.js`) and Twitch always shows its consent screen (`force_verify`).
- **YouTube Shorts:** Detected via YouTube Data API duration check (≤ 180 s, `SHORTS_MAX_SECONDS`), separate notification format. A video that is a livestream (or about to be one) is skipped by the feed poller; the live poller announces it.
- **User feedback:** Star rating + message on account page, visible in admin Feedback tab.
- **Admin panel:** Admin tab on dashboard (admin-only). Tabbed: Stats / Users / Issues / Feedback / Discounts / Testing. **Admin is decided by Discord user id only** (`src/adminAccess.js`): the built-in default id plus any comma-separated ids in `ADMIN_DISCORD_IDS` (entries that are not numeric ids are ignored; names and usernames never count). `db.isAdmin()` is the single check, `config.adminDiscordIds` the list, and every id on it also gets the enterprise-tier seed row at boot. A Racing account is admin only through the streamer it is linked to. **Disable** (`accountLifecycle.js`, `streamerAccess.js`) turns an account into a logged-out visitor everywhere: its sessions are deleted, `/dashboard` shows an "Account disabled" page, its overlay links (alerts, sponsors, goal, sounds, VTuber) answer like an unknown token, and its EventSub, StreamElements, Twitch and YouTube live chat and sponsor rotations are stopped (Enable restarts what it had on; a YouTube chat it was polling resumes if the account is enabled again within 30 minutes). Welcome messages and `/link` skip a disabled account's claim of a server, and the Atleta Racing app's account and Spotify calls treat a disabled streamer as no linked streamer. **Remove** deletes every row the account owns (`STREAMER_OWNED_ROWS` in `db.js`; uploaded files stay on disk). An admin cannot disable or remove their own account. **Issues:** a reported issue gets an AI analysis (`agentTriage.js`; needs `ANTHROPIC_API_KEY`, model `TRIAGE_MODEL`) at most once per issue and 5 per streamer a day (`issueAnalysis.js`); the auto-fix/PR feature is gone.
- **Custom Overlays (DISABLED):** Code exists (`customOverlays.js`, `scenes.js`, `bar.js`, `custom-alerts.js`, `custom-overlays.ejs`) but all integrations commented out in `server.js`, `overlay.js`, `twitchChat.js`, `dashboard.ejs`, `overlay-builder.ejs`, `overlay-config.ejs`, `overlay.css`. DB table `custom_overlays` exists. Re-enable by uncommenting the marked sections.
- **Password reset:** `password_reset_tokens` table. Self-service via email (`nodemailer` + Gmail) at `/racing/auth/forgot` → `/racing/auth/reset` works only when `EMAIL_USER` and `EMAIL_PASS` are set; production has no email configured, so the form answers "Email service not configured. Contact an admin." and the real path is the admin-generated link: Racing admin panel "Reset PW" button (`POST /racing/admin/reset-password/:id`, 24h link), also `POST /admin/racing-reset-password` (Discord admin auth).
- **iRacing Web Integration (coming soon):** Built but disabled — waiting for iRacing OAuth credentials.
- **DB migrations:** Auto-run on startup in `src/db.js`; the ones that add `streamers` columns run after its `CREATE TABLE`, so a brand-new database has every column after its first boot. SQLite pragmas applied at startup: `journal_mode=WAL`, `foreign_keys=ON`, `synchronous=NORMAL`, `cache_size=-64000`, `temp_store=MEMORY`, `mmap_size=256MB`. Hot-path indexes on `subscriptions(streamer_id, status)`, `watched_channels(twitch_username)`, `watched_youtube_channels(youtube_channel_id)`. A change to stored values (not to the schema) that must happen once goes through `_runOnce(name, fn)`, which runs it in a transaction and records the name in `data_migrations`. `src/db.test.js` boots a fresh database; CI boots twice on one and fails on any `[DB migration]` line.
- **Boot and shutdown (`src/index.js`):** the web server and everything that does not need Discord (EventSub, StreamElements, the Twitch chat bot, sponsor rotations, giveaways, housekeeping, nightly backups) start at boot (with the relay configured, also the multistream broadcast reconcile and then the relay check every minute); slash commands, welcome messages and the pollers start on Discord's `clientReady`. A failed Discord login is retried in the process (`src/services/discordLogin.js`: 30 s, doubling to every 10 min) while the site keeps running, and a token Discord refuses is logged loudly and not retried; until the bot is ready the dashboard builds the bot invite from `DISCORD_CLIENT_ID` (discord.js has no application until then); `DISCORD_DISABLED=1` (dev/CI only) skips Discord entirely. On SIGTERM/SIGINT the server stops taking connections, ends the SSE streams (each SSE route registers with `httpDrain.holdStream(res)`; OBS reconnects to the new server), waits up to 10 s for requests in progress, stops the pollers, chat, EventSub, StreamElements, YouTube chat, sponsors, the multistream checks, a waiting Discord login retry and Discord, closes the DB and exits 0. Also at boot, before anything serves: the legacy shared alert sounds move into their owner's folder (`customSounds.migrateLegacySounds()`) and watchers of servers a streamer no longer has are removed (`db.deleteOrphanWatchers()`).
- **Health:** `GET /health` (`src/health.js`) answers 200 `{"ok":true}` after `SELECT 1`, 503 `{"ok":false}` when the DB fails; no auth, registered first (ahead of the HTTPS redirect, rate limits and session lookup).
- **Backups** → `docs/operations/backup-restore.md`. `src/services/backups.js` writes `data/backups/bot-YYYY-MM-DD.db` every night at 03:30 UTC with SQLite's online backup API (`db.backupInto()`: a few pages at a time, so the app never pauses), keeps 7 days and always the newest copy, and on a night with no room for a copy still removes the ones past 7 days; nothing serves `data/backups/`. Railway volume backups are separate (set in the Railway dashboard).
- **Request bodies:** 100 kb for JSON and forms everywhere, except the routes in `LARGE_BODY_ROUTES` (`src/bodyParsers.js`: session 10 MB, lap 5 MB, track map 5 MB, bridge logs 3 MB, imports 10 MB, issue/bug reports 1 MB, racing pictures 2 MB), whose parsers run before the global ones. A parser placed on a route itself never runs (the global one has already read the body), so a route that needs more must be added to that table.
- **CSRF:** `src/csrf.js`, mounted after the session middleware and the body parsers, ahead of every route. A POST, PUT, PATCH or DELETE must name this site in its `Origin` (or, without one, its `Referer`): `APP_URL`'s origin or the one the request was sent to; `Origin: null` never counts. With a logged-in session it must also carry the session's token, `HMAC-SHA256(CSRF_SECRET, the stored session id hash)`, as a `_csrf` field or an `X-CSRF-Token` header (the field is removed before the route sees the body). Refusals answer 403: JSON `{ ok: false, error }` to a script, the error page to a form post, asking to reload. helmet's `Referrer-Policy` is `same-origin`: under its default (`no-referrer`) browsers send form posts with `Origin: null`. Logout is a POST (`/auth/logout`, `/racing/auth/logout`); a GET only redirects.
  - **Adding a form or a `fetch` to a page:** pages get the token as `res.locals.csrfToken`. `header.ejs` includes `views/csrf.ejs`, which loads `public/js/csrf.js` (adds `_csrf` to POST forms as they are sent, `form.submit()` included, and `X-CSRF-Token` to same-origin unsafe `fetch()`/`XMLHttpRequest`), so a page that includes the header needs nothing more. A view that does not include the header must include `csrf.ejs` in `<head>` itself (`overlay-builder.ejs`, `tip.ejs`; the two pages `racing-auth.js` writes out use `csrfScript(res)`); `src/csrf.test.js` checks every view and fails when one is missing.
  - **Adding a route that a program, not a browser page, calls with an unsafe method** (the Atleta Racing app, the multistream relay, a webhook): add it to `CSRF_EXEMPT` in `src/csrf.js` with its reason, or it gets 403 (`[CSRF] Refused ...` in the log). An exempt route skips only the Origin check: a request to it that carries a logged-in session still needs the token. Today's list: the Atleta Racing app's calls, the multistream relay, `/sync/trigger`, the public tip form.
- **Rate limits:** every limiter keys on `byVisitor` in `server.js` (the address `src/clientIp.js` gives, see Conventions; an IPv6 visitor counts by their /56, through `ipKeyGenerator`): `generalLimiter` 200/min on everything; `authLimiter` 5 per 15 min on `/racing/auth`; `apiLimiter` 150/min mounted once as `app.use('/api', apiLimiter)` ahead of the body parsers and every `/api` route (a refused request is answered before its body is read) (reads of a single track map are not counted) — the multistream relay's own requests (`/api/multistream/*` carrying `MEDIAMTX_WEBHOOK_SECRET`) count toward neither limit — never add it to an individual `/api` route again (it would count twice); `/api/voice/:discordUserId` has its own 60/min (the Bridge overlay polls every 2 s).
- **Uploads and uploaded files:** dashboard uploads go through `refuseUpload()` (`src/services/storageQuota.js`): refused with 507 and a translated message when the data volume would keep less than 200 MB free, or (sounds, sponsor images, reward clips, VTuber models) when the streamer's media in `data/{sounds,sponsors,redemptions,vtuber-models}/<id>/` would pass 250 MB. Every route that serves uploaded files (`/sponsors`, `/redemptions`, `/avatars`, `/issues-files`, `/vtuber-models`, `/overlay/sounds/:token/:type`) sends `src/services/userContentHeaders.js`'s headers: `Content-Security-Policy: sandbox; default-src 'none'`, `nosniff`, and `Content-Disposition: attachment` for anything that is not an image, sound, video or model. Report screenshots (PNG, JPEG, GIF or WebP, never SVG) and sounds (MP3, WAV, OGG or M4A) are also checked by their first bytes (`uploadValidation.js`); reward media by type and extension (audio mp3/wav/ogg, video mp4/webm).
- **Discord voice API:** `GET /api/voice/:discordUserId` (public, used by the Bridge's Discord overlay) takes only a 17–20 digit snowflake and only reports a voice channel `@everyone` can view (`src/routes/voice.js`, `src/services/voicePresence.js`); a private channel answers like no channel.
- **Discord servers:** a streamer claims a server only with Manage Server in it (`canManageGuild`, checked again when the claim is made; "Available Servers" lists only servers they can manage). Every channel a notification, welcome message or mod-log post goes to must belong to its server: `src/discord.js` (`fetchGuildChannel`, `sendToGuildChannel`) is the only place that sends, saved channel ids are checked with `channelsInGuild`, and a failed post is recorded on the `guilds` row (`last_delivery_error*`) and shown on the server page. While the bot cannot see a server (Discord not ready, down or refused) the server page keeps the saved welcome channel and sub role, saves the rest and says so, and the Edit forms of watched channels change nothing. The sub-sync role must be a plain role below the bot's top role — not `@everyone`, not managed, none of Administrator, Manage Server/Roles/Channels/Webhooks, Kick, Ban or Timeout (`subRoleEligibility`; a role that may mention @everyone is allowed: whoever picks it decides); `subSync` re-checks it every cycle and skips a server whose role stopped qualifying. Welcome messages are capped at 4000 characters. A new bot invite asks for six permissions (`268553216`: View Channel, Send Messages, Embed Links, Attach Files, Read Message History, Manage Roles), not Administrator; servers invited earlier keep what they granted. Removing a server removes its watchers. A server watches at most 25 Twitch channels (`config.limits.twitchChannelsPerGuild`); a name is normalised (`twitchLogin.js`) and checked with Twitch before it is added.
- **Secrets at rest:** `TOKEN_ENCRYPTION_KEY` (64 hex characters) seals the OAuth tokens (Twitch broadcaster, YouTube, Spotify, the bot's) and the StreamElements token in `streamers` as `enc:v1:` AES-256-GCM text (`secretBox.js`). Every write goes through `sealToken()` and every read of a `streamers` row through `openToken()`/`openTokens()` in `db.js`; `src/db.secrets.test.js` scans the SQL and fails when a query reads or writes a token column outside them (a new token column goes in `TOKEN_COLUMNS`). Without the key tokens stay unencrypted (one boot warning); a sealed value that cannot be opened reads as "not connected" (never sent anywhere) and the boot logs how many; a malformed key stops the boot. Never change or lose the key, and never roll back to a release from before it was introduced once it is set: `docs/operations/deploy.md`. A development copy made with `/sync` carries only sealed tokens.
- **EventSub (`eventsub.js`):** one session socket per streamer; on Twitch's `session_reconnect` the new socket is used as given (no resubscribing) and the old one stays open, acted on for notifications only, until Twitch closes it or 30 s pass; a connection attempt Twitch never answers is given up after 10 s, and a socket that gets no welcome is replaced after 15 s (the default 10 s keepalive plus 5 s); the subscribe loop follows a session that moved, with its new id; a notification whose `message_id` was seen in the last 10 minutes is ignored (`messageDedupe.js`); a stopped client never reconnects. The boot line counts only the streamers that got a connection (`Started N connections`, with how many were skipped). Gift subs give one alert and one thank-you per `channel.subscription.gift`; the per-recipient `channel.subscribe` events with `is_gift` are ignored.
- **Pollers (`src/pollers/`):** every poller runs through `exclusiveRun.js` (a tick is skipped while its previous run is going; a run older than 15 minutes is given up on). Twitch live checks ask for up to 100 logins per request (`getStreams`, `chunk.js`) and a failed batch leaves its channels as they were; a stream is over, and its recap sent, only on the second empty poll in a row (recaps arrive about a minute after the stream ends), and the same broadcast id coming back is not announced again (`channel_state.last_stream_id`, `offline_polls`). Milestones are evaluated when a stream starts, and the first look at a channel only records the baseline. The weekly digest ticks every 15 minutes (`WEEKLY_DIGEST_INTERVAL`) and posts in the Monday 09:00 UTC hour; a post that failed is tried again (first try plus 3 retries, 10 minutes apart) and the week is recorded only when a post went out. `sendNotification()` returns whether the post went out (false: a channel the bot cannot reach; Discord errors still throw), so a caller that records or counts posts must check it. A title or description that comes from Twitch or YouTube (a clip's or video's title, a YouTube channel name, a live stream's description) goes through `escapeLinkText()` (`src/discord.js`) before it goes into a Discord post, so its brackets cannot become a link; the post's URL is left as it is. YouTube: a spent quota pauses both YouTube pollers for an hour, and without `YOUTUBE_API_KEY` the live poller does nothing.
- **Giveaways** (`giveawayManager.js`, `/dashboard/giveaways`): a chat keyword opens entries; `pickWinners` draws once (a second pick answers the winners already drawn) unless asked to re-draw; winners get an overlay card (`giveaway_winner`) and a chat line. A giveaway cannot start while the streamer's chatbot is off (`chatbot_off`): the chatbot collects the entries. A giveaway that is due when the app boots is closed and drawn no sooner than 30 s after the boot (so the chat bot and OBS are back for the chat lines and the winner card) and takes no entries past its end time. `overlay_giveaway_duration` is stored in **seconds** (default 10, clamped 1–60), like the other alert durations.
- **Errors and deadlines:** `src/errorHandler.js` is the last middleware, so a thrown error is logged with the route pattern (never the real token in the URL) and the visitor gets a generic page, or `{ error: 'Internal error' }` for API/JSON requests, never a stack. Redirects carry error *codes* (`?error=not_found`), never text; the page maps a code it knows to a `t()` key (`errorMessage()` in `donationSettings.js`). Outbound calls have deadlines (`AbortSignal.timeout()`: 10 s for Helix and OAuth), and a dashboard page never waits on Twitch or YouTube for more than 3 s (`pageLookups.js`; missing channel pictures are filled in after the page is sent). The test buttons share one cooldown per streamer, 5 s (`testCooldown.js`).
- **No ORM:** All SQL is raw in `db.js`.
- **i18n:** `t(lang, key, params)` helper via `res.locals.t` (`esc()` and `rich()` are on `res.locals` next to it, set in `src/server.js`); the language is the `lang` cookie (the language switcher), else English; the browser's `Accept-Language` is not used. Every streamer page and the public tip page are translated into the 7 languages: no English typed into a view, every key in `en.json` exists in all 7 locale files with the same `{{placeholders}}` and no empty text, and every key the source names is in `en.json` (`tests/i18n.test.js` enforces it), a sentence with a link, bold word or code is printed through the escaping `rich()` (with `esc()` for plain values; never `<%- t() %>`), a page's script gets its texts as one JSON object, and error codes — not texts — travel in URLs. How to add a string or a page, the tests that guard it and what is deliberately not translated: `docs/features/i18n.md`.

## Conventions

- Plain CommonJS (`require`/`module.exports`), no ESM.
- No framework abstractions — routes, DB queries, and pollers are straightforward procedural code.
- All database operations go through `src/db.js`.
- Config access via `require('./config')`.
- `-1` means unlimited in tier limits.
- CSS design system uses CSS custom properties (defined in `header.ejs`).
- Typography: Outfit (display) + DM Sans (body) via Google Fonts.
- All user-facing text uses `t('key')` — views, the texts a page's script needs, and the answers of routes. No English typed into a view; a new key goes into all 7 locale files (`tests/i18n.test.js` fails without them; `docs/features/i18n.md`).
- Twitch notifications sent as embeds, clips and YouTube videos sent as plain text (for Discord auto-preview).
- Custom alert sounds are stored per streamer in `data/sounds/<streamerId>/<type>.mp3` (persistent volume) and served by `GET /overlay/sounds/:token/:type`; there is no shared sound folder (`public/overlay/sounds/` is an empty placeholder, not a place for sounds).
- Sponsor images stored in `data/sponsors/<streamerId>/`, served via the `/sponsors/` static route.
- Channel point reward media stored in `data/redemptions/{streamerId}/`, served via `/redemptions/`. Filenames are `{rewardId}_{timestamp}.{ext}` so the 24h cache headers stay safe across replacements.
- **EJS templates DO NOT have access to `require()`.** Express's EJS integration runs templates in a sandboxed scope. If a view needs a value derived from a service module, the route handler must compute it server-side and pass it as a template local. Inline `<% require('...') %>` will throw "require is not defined" and crash the page in production. Reference: `routes/dashboard.js` `GET /redemptions` precomputes `hasScope` via `hasRedemptionScope(req.streamer)` and passes it to `redemptions-config.ejs`.
- **Views:** a view that includes `header.ejs` ends with `<%- include('footer') %>` (`tests/headerView.test.js`); a value a page prints into its own script as JSON ends in `.replace(/</g, '\\u003c')` so it cannot end the script (`tests/scriptEmbeds.test.js` checks every `<%- JSON.stringify(...) %>`). The icon library (lucide) loads from one exact version with its `integrity` sha384 in `header.ejs` and `racing-pitwall.ejs`; to move it, download the file, take `openssl dgst -sha384 -binary lucide.min.js | openssl base64 -A` and change both tags (a hash that does not match makes the browser refuse the script, and every icon disappears).
- **Client/server query-param parity for raw-body uploads.** Sponsor/redemption uploads send file bytes in the body and metadata in `?...` query params. The exact param names must match the server's `req.query.X` reads — a mismatch is silent (e.g., empty title gets re-rejected by length validation with a confusing error). When changing one side, verify the other.
- Overlay designs stored in `overlay_designs` table (including `card_custom_x`/`card_custom_y` for drag positions, advanced theme: `bg_opacity`, `gradient_direction`, `border_thickness`, `border_opacity`, `glow_intensity`, `shadow_*`), applied at runtime in `overlay.js` via `applyCustomDesign()`.
- `applyCustomDesign()` must NOT overwrite dynamic detail text for donations/subs/bits/raids — only for follows.
- Tab persistence uses `localStorage` across all tabbed pages.
- Open Graph meta tags in `header.ejs` for social sharing previews.
- Domain: `atletanotifications.com` (Cloudflare DNS → Railway).

## Overlay Consistency Rule

**The overlay builder (`overlay-builder.ejs`) is the source of truth for how alerts look.** The actual OBS overlay (`overlay.js` + `overlay.css`), the overlay config preview (`overlay-config.ejs` iframe), and the builder preview must all render cards identically:

- **Placement:** where an alert sits (the nine grid cells, a dragged `card_custom_x/y`, and `card_width`) is read from the saved design by `public/overlay/placement.js`, which both the OBS overlay (`applyPlacement()`) and the builder preview (`positionCard()`) use. The five object types honour position and width; their colours and animations are not styled yet.
- **Object registry:** The five Twitch event types (`follow`, `subscription`, `bits`, `donation`, `raid`) render from `public/overlay/objects/`. Any change to an object's markup, keyframes or timing is made there and nowhere else — both render paths (the OBS overlay `overlay.js` and the builder preview `overlay-builder.ejs`) consume the same module. Styles (`STYLES` in `objects/index.js`, `window.ATLETA_OBJECT_STYLES` in the browser) are objects filed under a style id with the `eventType` they draw; both render paths pick an alert's object with the same rule (`objectFor()` in `overlay.js`, `previewObjectFor()` in the builder; `tests/overlayBuilder.test.js` fails when the two picks differ: "the preview and the OBS overlay pick the same object for every alert and style"). `STYLES` is a non-enumerable property of the CommonJS export, so `Object.keys(OBJECTS)` is still the five. `overlay-config.ejs` previews via an iframe of the real overlay and needs no parallel change. Every object-internal CSS class MUST be namespaced under its `.o-*` prefix; a bare `.rail` collides with the builder page's sticky control bar, as shown in the prototype at `docs/superpowers/specs/assets/2026-10-09-alert-objects-prototype.html`. Remaining event types still share the legacy `top-accent` + `card-body` + `car-track` structure, whose markup `buildBannerContent()` in `overlay.js` builds.
- **Looks:** the alert looks (`objects/kit.js`, `objects/styles/`) are drawn by both pages from the same files. The builder's `previewObjectFor` and the overlay's `objectFor` pick with the same rule (`tests/overlayBuilder.test.js` runs both). A look's data comes from `kit.lookData`, its colour and speed from `kit.slotVars`, its effect and sound from `kit.effectFor`/`kit.soundFor`, and its five new screen effects from `fx.js` (`spawnEffects` and `renderScreenEffect` both call `ATLETA_FX.spawn`).
- **Screen effects:** Direction-based effects (up/down/left/right) must work in both the builder preview (`renderScreenEffect()` in overlay-builder.ejs) and the OBS overlay (`spawnEffects()` in overlay.js). CSS classes for effects must NOT hardcode positional properties (`top`, `left`, etc.) — positions are set dynamically by JS based on direction.
- **Design application:** `applyCustomDesign()` in overlay.js and `updatePreview()` in overlay-builder.ejs must apply the same visual properties (colors, fonts, sizes, border-radius, animations, side icons). The default side icons are the builder's table: `DEFAULT_SIDE_ICONS` in overlay.js lists the alerts the builder gives one (`tests/overlayClient.test.js` fails when they differ). A legacy card fades out only once its entrance is taken off (`.entering` and the inline `animation`), because the entrance's last frame holds the opacity.
- **When adding/changing any visual property:** Update all three places — the builder preview (`updatePreview()` in `overlay-builder.ejs`), the OBS overlay (`buildBannerContent()` and `applyCustomDesign()` in `overlay.js` for the legacy cards; the five Twitch events come from `public/overlay/objects/`, which both pages already share), and the shared defaults and save schema in `src/services/overlayDesign.js` (`EVENT_DEFAULTS`, which the route injects into the builder page, and `FIELD_SPECS`; `overlayDesign.test.js` fails when the builder's controls drift from them).
